# routing-arena-demo

路由策略池竞技场 demo —— 用历史日志回放，让不同"选渠道策略"同场 PK，
用数据决出最优解（省多少钱 / 快多少 / 稳不稳）。

> v6 方法论升级（2026-10-09）：数据源换成**模拟生成器**（多渠道/多模型/小时曲线/
> 涨价/故障窗口），评估升级为**样本外 + 真值判官 + 置信区间**。见
> [`docs/v5-v6升级对照.md`](docs/v5-v6升级对照.md)。

## 快速开始

```bash
go test ./...            # 全量测试（12 个包）
go vet ./...             # 静态检查

go run ./cmd/arena       # 影子竞技场：S0/S1/S2 样本外回放对比（真值 + 置信区间）
go run ./cmd/p1          # P1 真实小流量验证（5% 混流 vs 理论预期）
go run ./cmd/p2          # P2 看板选优：评分（带 95%CI）+ 晋升建议 + 熔断回滚
go run ./cmd/p3          # P3 健康探测 + 自动模式 + 二次确认 + 全程留痕
go run ./cmd/scenarios   # 场景矩阵：正常/单点故障/限流/涨价/高峰并发
go run ./cmd/p4          # 第三波能力：自适应权重/会话粘性/约束选路/指标下钻
go run ./cmd/admin       # 管理后台 (:8080 / ADMIN_PORT 可改；ADMIN_TOKEN=xxx 开鉴权，-data 目录落盘)
```

数据源：默认模拟生成（`-records`/`-seed` 可调）；传 `-csv 路径` 用自己的 CSV。
所有 `cmd` 统一从 `internal/sim` 取数（`sim.LoadOrGenerate`），将来接生产网关真实消费日志时只需改这一个入口。

| 策略 | 类型 | 作用 |
|------|------|------|
| S0_Champion | 保底 | 基线，永不熔断 |
| S1_MinCost | 极端探底 | 永远最便宜 |
| S2_MinLat | 极端探底 | 永远最快 |
| S3_Hybrid | 综合实战 | 成本/延迟/健康度加权（P2C 选路） |
| S4_Robust | 综合实战 | 大促/故障期保稳 |
| S5_Constrained | 业务口径 | 延迟 ≤1.5s 里挑最便宜（实时探测做约束） |

## 方法论要点（v6）

- **样本外评估**：前 70% 日志建知识库（策略"见过"的历史），后 30% 做评估（没见过），
  避免"用同一批数据既定价又评分"的样本内自证。
- **真值判官（Oracle）**：成本/延迟用生成器画像（`sim.Oracle`）算，S0 与候选
  策略在同一把尺子下比，不再用知识库均价给自己打分。
- **统计显著性**：节省率带 95% 置信区间（小样本用 t 分布），候选成本区间整体
  低于 S0 才算"省得显著"；样本不足 30 不参与晋升。
- **熔断器真正接入回放**：每次请求结果回告熔断器（`ReportOutcome`），策略老选
  故障渠道 → 失败率超阈值 → 熔断 → 自动回退，单点故障场景里把损失兜住。
- **水位拦截引擎级化**：并发水位对所有策略生效（候选池先过滤，再交策略算分）。

## 能力翼（第三波，v6）

- **时段自适应权重**：S3/S4 按小时换评分权重（白天 25/45/30 重延迟，夜间 50/20/30
  重成本）。只在"快 or 便宜"冲突时起作用；存在又快又便宜的渠道时所有权重都选它。
- **会话粘性（sticky）**：同一用户固定走同一渠道（前缀缓存命中、感知稳定），
  渠道不可用自动解除绑定；演示里切换次数从 357 → 0，成本基本持平。
- **约束式选路 S5**：实时延迟 ≤1.5s 的渠道里选最便宜，全超限时兜底选最快。
  关键：约束判断必须用**实时探测**延迟，不能只看历史平均（看不到正在故障的渠道）——
  演示里 S5 避开故障渠道5，得到 1070ms/0.675 的中间解（S1=3200ms/0.556，S2=520ms/0.715）。
- **Prometheus 指标 + 毛刺下钻**：`/api/metrics` 输出延迟直方图（无第三方依赖，
  手写 Prometheus/OpenMetrics 文本格式），每条样本挂 `trace_id` Exemplar——
  看板点毛刺即可跳到具体那一条请求的完整决策链（v5 方案里 OTel Exemplar 的 demo 版）。

## 治理翼（第二波，v6）

- **后台鉴权**：`ADMIN_TOKEN=xxx` 开启，变更 API 需 `Authorization: Bearer`；空 = 开发模式。
- **操作人审计**：每次手动切换/参数变更记录 `X-Operator`（默认 admin）进历史。
- **二次确认**：切冠军必须显式 `confirm:true`，防手滑。
- **JSONL 审计落盘**：`-data 目录` 开启，切换历史 + 告警写 JSONL，重启可查、可恢复。
- **告警**：熔断触发 / 手动切换 / 故障注入写 alerts，`/api/alerts` 可查。

## Benchmark（`go test -bench=P2C -benchmem`）

| 候选数 | P2C | 全遍历 | 说明 |
|--------|-----|--------|------|
| 4 | 162 ns | 144 ns | 小池子 P2C 反而略慢（随机数开销） |
| 16 | 519 ns | 536 ns | 基本持平 |
| 64 | 1808 ns | 2041 ns | 快 ~11% |

结论：**P2C 只省"算分"阶段（O(N)→O(1)），候选池收集仍是 O(N)**；渠道多时才有
可感知收益，渠道少时不要为了"先进"引入它。真实网关若渠道几十个，P2C 值；若个位数，
收益可忽略。
